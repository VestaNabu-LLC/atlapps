Jira permission audit checklist

Who can see and change what in your Jira Cloud site? Six checks you can do by hand, with the menu paths Jira uses today. Plan on an hour for a small site.

Before you start

  • You need the Administer Jira global permission. To review group members you also need access to Atlassian Administration (admin.atlassian.com).
  • Have a document or spreadsheet open to note each finding, where it is and what you decided.
Names changed. Jira Cloud now calls projects spaces and issues work items. This checklist uses the new names. Older articles and screenshots use the old ones.

Jira sites grow for years. Spaces get created, filters get shared with everyone, a contractor gets an admin role and keeps it. Nobody decides to leave the doors open; it accumulates. These checks find where it happened.

1. Permission schemes: who can see, change and delete

  1. Go to Settings (the gear icon) → Work items → Permission schemes. Note every scheme and which spaces use it.
  2. Open each scheme's permissions and read who holds the sensitive ones: seeing a space at all (the browse permission), administering it, editing, deleting and moving work items, and deleting other people's comments and attachments.
  3. Look for these holders. They are where most real exposure comes from:
Holder, as Jira shows itWho that isHow serious
PublicAnyone on the internet, without logging inFix first
Any logged in userEveryone who can log in to the siteCheck intent
Application accessEveryone with access to the Jira productCheck intent
Single userOne named person, whose access stays with them when they change teamsTidy up
Group, Space rolesThe normal way to grant accessCheck members
  1. For each hit, ask whether it is intended. Public on the browse permission of a space that is not meant to be public is the finding to fix first.
  2. Note schemes that no space uses. They are clutter, and a trap if someone attaches one to a new space later.

Example, illustrative: a scheme named "Default" grants the browse permission to Public and is used by 14 spaces. Every work item in those spaces can be read by anyone, without logging in.

2. Global permissions: who runs Jira

  1. Go to Settings → System → Global permissions.
  2. List every group and user that holds Administer Jira. These are the groups to review in step 3.
  3. Note who holds Share dashboards and filters. If it is everyone, expect many shared filters in step 5.
  4. Prefer groups over individual users here, so access ends when someone leaves a group.

3. Admin groups and inactive admins

  1. In Atlassian Administration, open Directory → Groups and open each group from step 2.
  2. Check every member: still with the company, still needs admin, account still active.
  3. Deactivated or suspended accounts sitting in an admin group are the quickest wins: remove them.
  4. Keep the admin group small and named. Fewer admins means fewer accounts that can open everything up.

4. Space roles

  1. Go to Settings → System → Space roles (formerly project roles). For each role, Manage Default Members shows who new spaces get by default. Changes there apply to new spaces only.
  2. For each important space, open Space settings and its people page (People in company-managed spaces, Access in team-managed ones). Compare who holds each role with who should.
  3. Look for roles held by very large groups, and for people who moved teams but kept their role.
  4. Most permission schemes grant access through roles, so one over-wide role quietly widens every permission that role holds.

5. Shared filters and dashboards

  1. Go to Settings → System → Filters to search the site's shared filters. Admins can change a filter's owner or delete it there.
  2. Go to Settings → System → Dashboards (under Shared items). The search shows each dashboard's owner and who it is shared with.
  3. Flag anything shared publicly (anyone on the web) or with every logged-in user.
  4. A shared filter only leaks if its JQL returns work items the audience should not see, so open each flagged one and read the query. Dashboard gadgets can show work item summaries too.
  5. Unshare or delete what nobody needs. If the owner has left, change the owner first.

6. Record it and repeat

Write down the date, what you found and what you changed. Repeat every quarter, or before each security audit (SOC 2, ISO 27001). The first pass is the easy part. The hard part is noticing next quarter what changed since the last one.

Automating it
